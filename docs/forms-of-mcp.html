Forms of MCP

MCP has three independent sets of forms: what a server may expose, how it is reached, and what shape of problem it solves. Filter the protocol surface by what is still current, explore the patterns, or describe what you are building and see which forms it wants.

Primitives, by who pulls the trigger

The real difference between the three is not what they hold. It is who decides to use them. A document served as a resource costs nothing until the host attaches it; the same document behind a tool costs a model decision and a round trip.

No primitives at this status.

Tool results carry content, optional structuredContent, and isError. A failure inside the tool is a normal result with isError: true, which the model can read and react to. A protocol failure is a JSON-RPC error, which it cannot. Putting a business failure in the wrong one is a common bug.

What the client offers back

This is the part that changed most in 2026. Server-initiated requests are gone entirely: a server may no longer send roots/list, sampling/createMessage, or elicitation/create as separate requests.

The deprecation clock

Deprecated features stay in the spec for at least twelve months from this revision. The registry puts the earliest removal at the first revision released on or after 28 July 2027, and removal is a maintainer decision that may land later. Code written against sampling or roots today still runs; code written against them tomorrow is a migration you have chosen.

Transports, which decide the architecture

Transports
TransportStatusShape, and what it suits
stdioCurrent The client launches the server as a subprocess and speaks newline-delimited JSON-RPC over its pipes. No port, no URL, no daemon; it lives and dies with the session. The only form that can see the machine. Authorization does not apply: credentials come from the environment.
Streamable HTTPCurrent One endpoint accepting POST, answering with JSON or a request-scoped SSE stream. The form for anything multi-tenant. Each POST carries MCP-Protocol-Version, Mcp-Method, and Mcp-Name on the three named methods; Origin must be validated; closing the stream is how a call is cancelled.
HTTP+SSEDeprecated The original two-endpoint remote transport, deprecated since revision 2025-03-26 and reclassified under SEP-2596. Removal is set three months after that proposal reaches Final.
CustomPermitted Any carrier preserving the JSON-RPC format, the message patterns, and per-request metadata. Byte-stream carriers should reuse the stdio framing.

No transports at this status.

This is the choice people get wrong first, usually by asking for a URL. A remote server cannot see your filesystem, so the moment the work involves uncommitted files or a command that must run on this machine, the transport decides the architecture. The alternative is uploading the data, which is a different product with different consent questions.

The stateless turn

Revision 2026-07-28 removed the handshake. No initialize, no notifications/initialized, no Mcp-Session-Id, no GET stream endpoint, no Last-Event-ID resumability. Every request carries its own context.

The point is deployment shape. A stateless server sits behind an ordinary load balancer, scales horizontally, and survives a restart mid-conversation. The cost is that state must become explicit, and the spec's own guidance is to hand it back as a value: a creation tool returns basket_id, and every later call passes it as an argument.

Multi round-trip requests, step by step

Removing sessions broke the one thing that needed them: a server interrupting its own call to ask for something. MRTR moves that interruption into the result. Step through it.


    

    
Every result now carries a required resultType, one of
      complete or input_required, with task added by the Tasks

      pattern applies only to tools/call, resources/read, and

One security consequence

      
requestState travels through the client, so it is attacker-controlled. If it
        influences authorization or business logic, the server must integrity-protect it with an HMAC
        or AEAD and reject what fails verification. The spec does not guarantee single use, so
        anything that must happen once has to be enforced server-side.

    

  


  

    
Extensions, the forms outside the core

    
Capabilities not ready to be mandatory live as named extensions, identified as
      {vendor-prefix}/{name} and declared by both sides. Either side lacking one falls
      back to core behavior. Stages run Experimental, Beta, Stable.

Authorization, for anything remote

    
Remote servers are expected to conform to the OAuth 2.1 draft with a specific
      discovery chain. A 401 carries WWW-Authenticate with resource_metadata;
      the client follows RFC 9728 protected resource metadata to find the authorization server, which
      must publish RFC 8414 or OpenID Connect discovery.

    
Two requirements catch people out. Clients must send the RFC 8707
      resource parameter, set to the server's canonical URI, in both the authorization and
      token requests, even when the authorization server ignores it; and the server must validate that
      a token's audience is itself, so a token minted for another service cannot be replayed at it.
      Dynamic Client Registration is now deprecated in favor of Client ID Metadata Documents or
      pre-registration. Tokens go in the Authorization header, never a query string.
